# 착수보고서 작성 기준 (Writing Guide)

PM 표준(PMI/PRINCE2) 기반 착수보고서 9개 섹션별 작성 기준, 좋은 예·나쁜 예, 체크리스트.
HTML 시각화 시 이 파일의 구조를 기반으로 `report` 타입 레이아웃을 생성한다.

---

## 섹션 1. 프로젝트 개요 (15점)

**목적**: 이 프로젝트가 왜 필요한가를 3가지 관점으로 명확히 서술한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| 목적 | 왜 이 프로젝트를 수행하는가 (문제 진술) | □ |
| 배경 | 현재 상황, 데이터 근거 | □ |
| 기대 효과 | 측정 가능한 비즈니스 이익 | □ |

### 좋은 예
> 현재 결제 API 평균 응답시간이 3.2초로, 업계 평균(0.8초)의 4배 수준이다.
> 이로 인해 월 결제 이탈률이 12%에 달하며 연간 약 18억원의 매출 손실이 발생한다.
> 본 프로젝트는 응답시간을 1초 이하로 개선하여 이탈률을 5% 이하로 낮추는 것을 목표로 한다.

### 나쁜 예
> 결제 시스템의 품질을 적절히 향상시킨다.

**핵심 원칙**: 숫자가 없는 기대 효과는 기대 효과가 아니다.

## 섹션 2. 범위 정의 (15점)

**목적**: 이번에 하는 것과 하지 않는 것을 명시적으로 구분한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| In-scope | 이번 프로젝트에서 다루는 기능/시스템 | □ |
| Out-of-scope | 명시적으로 제외하는 것 | □ |
| 주요 산출물 | 프로젝트 완료 시 나오는 결과물 목록 | □ |

### 좋은 예
**In-scope**: 결제 API 성능 최적화, 캐싱 레이어 도입, 모니터링 대시보드 구축
**Out-of-scope**: UI/UX 개편, 신규 결제 수단 추가, 정산 시스템 변경
**산출물**: 최적화된 결제 API v2.0, Grafana 대시보드, 성능 테스트 보고서

### 나쁜 예
> 결제, 정산 등 관련 기능을 개선한다.

**핵심 원칙**: Out-of-scope가 없는 범위 정의는 범위 정의가 아니다.

## 섹션 3. 일정·마일스톤 (15점)

**목적**: 프로젝트 진행 상황을 측정할 수 있는 체크포인트를 정의한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| 시작일·종료일 | 확정된 날짜 (추후 확정 불가) | □ |
| 마일스톤 3개 이상 | 날짜 포함, 완료 기준 명시 | □ |
| 의존관계 | 마일스톤 간 선행 조건 | □ |

### 좋은 예
| 마일스톤 | 일정 | 완료 기준 |
|---------|------|---------|
| 요구사항 확정 | 2026-01-15 | 이해관계자 서명 |
| 설계 완료 | 2026-02-14 | 아키텍처 리뷰 통과 |
| 개발 완료 | 2026-04-18 | 단위 테스트 95% 이상 |
| UAT 완료 | 2026-05-23 | 결함 0건 (Critical) |
| 운영 이관 | 2026-06-07 | 모니터링 정상 확인 24h |

### 나쁜 예
> 1월 착수, 6월 완료 (상세 일정 추후 확정)

**핵심 원칙**: "추후 확정" 마일스톤은 마일스톤이 아니다.

## 섹션 4. 조직·R&R (10점)

**목적**: 누가 무엇을 결정하고 누가 책임지는지를 명확히 한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| PM 지정 | 이름, 연락처 포함 | □ |
| 팀원·역할 | 이름 + 담당 역할 | □ |
| 이해관계자 | 주요 의사결정자, 영향 받는 팀 | □ |
| 에스컬레이션 경로 | 이슈 발생 시 의사결정 흐름 | □ |

### 좋은 예
**PM**: 홍길동 (hong@company.com)
**개발**: 김철수 (Backend), 이영희 (Frontend)
**QA**: 박민준
**이해관계자**: 최CTO(최종 승인), 재무팀(예산), 운영팀(이관 수락)
**에스컬레이션**: 팀장 → PM → CTO (48시간 이내 미결 시)

### 나쁜 예
> 관련 팀과 협의하여 진행한다.

**핵심 원칙**: 이름 없는 R&R은 누구의 책임도 아니다.

## 섹션 5. 예산·자원 (10점)

**목적**: 재정적 범위와 인력 투입 계획을 수치로 제시한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| 총 예산 | 확정 금액 또는 상한선 | □ |
| 인력 계획 | 역할별 공수(M/M) 또는 FTE | □ |
| 예산 세분화 | 인건비, 인프라, 외주, 기타 | □ |

### 좋은 예
**총 예산**: 3.2억원
- 인건비: 2.0억원 (개발 3인 × 6개월)
- 인프라: 0.8억원 (서버 증설, CDN)
- 외주: 0.4억원 (보안 감사)
**예비비**: 10% (0.32억원)

### 나쁜 예
> 약 3억원 내외 (협의 예정)

**핵심 원칙**: "내외"와 "협의 예정"이 함께 있으면 예산이 없는 것이다.

## 섹션 6. 리스크·대응 계획 (15점)

**목적**: 발생 가능한 위협과 구체적 대응 전략을 사전에 정의한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| 리스크 식별 3건 이상 | 기술/일정/인력/외부 | □ |
| 영향도·가능성 | H/M/L 또는 점수 | □ |
| 대응 전략 | 완화(Mitigate)/회피(Avoid)/수용(Accept)/전가(Transfer) | □ |
| 리스크 책임자 | 모니터링 담당자 | □ |

### 좋은 예
| 리스크 | 영향 | 가능성 | 전략 | 대응 | 담당 |
|--------|------|--------|------|------|------|
| 레거시 코드 부채 | 높음 | 높음 | 완화 | 2주 선행 분석 스프린트 확보 | 김철수 |
| 외부 PG사 API 변경 | 높음 | 낮음 | 전가 | 계약서에 변경 통보 의무 명시 | 홍길동 |
| 핵심 개발자 이탈 | 높음 | 낮음 | 완화 | 지식 문서화 의무화, 페어 프로그래밍 | 홍길동 |

### 나쁜 예
> 리스크가 발생하면 신속히 대응한다.

**핵심 원칙**: 대응책 없는 리스크 목록은 위험 목록이 아니라 걱정 목록이다.

## 섹션 7. 전제조건·제약사항 (10점)

**목적**: 프로젝트가 참으로 가정하는 것과 변경 불가한 조건을 명시한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| 전제조건 (Assumptions) | 참으로 가정하는 것 | □ |
| 제약사항 (Constraints) | 변경 불가 조건 | □ |
| 외부 의존성 | 타 시스템·팀·벤더 | □ |

### 좋은 예
**전제조건**
- 인프라팀이 2월 1일까지 신규 서버 3대를 프로비저닝한다
- 보안팀의 아키텍처 리뷰가 설계 단계 내 완료된다

**제약사항**
- 운영 DB 스키마 변경 불가 (Zero-downtime 요구)
- 오픈 일정 변경 불가 (계약 기한 6월 30일)

### 나쁜 예
> 일반적인 프로젝트 조건을 따른다.

**핵심 원칙**: 전제조건이 깨지면 리스크가 된다. 전제와 리스크는 연결되어야 한다.

## 섹션 8. 성공 기준 (10점)

**목적**: 프로젝트가 완료됐다고 판단하는 조건을 측정 가능하게 정의한다.

| 필수 항목 | 설명 | 체크 |
|---------|------|------|
| KPI / 성공 지표 | 수치 기반 측정 지표 | □ |
| 완료 조건 | Done criteria (무엇이 완료되면 끝인가) | □ |
| 수락 기준 | 발주처·이해관계자 서명 조건 | □ |

### 좋은 예
**KPI**
- API P95 응답시간: 3.2초 → 1.0초 이하
- 월 결제 이탈률: 12% → 5% 이하
- 시스템 가용성: 99.5% 이상 (3개월 평균)

**완료 조건**
- UAT 통과 (Critical 결함 0건)
- 운영팀 이관 완료 및 24시간 모니터링 정상
- 최종 성과 보고서 발주처 승인

### 나쁜 예
> 시스템이 안정적으로 운영되면 완료로 간주한다.

**핵심 원칙**: "안정적"은 성공 기준이 아니다. 숫자가 기준이다.

## 섹션 9. 커뮤니케이션 계획 (보너스 +5점)

**목적**: 정보가 적시에 올바른 사람에게 전달되도록 채널과 주기를 정의한다.

| 권장 항목 | 설명 |
|---------|------|
| 보고 주기·형식 | 주간 진척 보고, 월간 경영진 보고 |
| 회의체 | 스탠드업, 스프린트 리뷰, 이해관계자 회의 |
| 이슈 관리 채널 | Jira, Slack, 이메일 에스컬레이션 경로 |

## 흔한 실수 Top 7

1. **PM 미지정 착수** — 의사결정자 없이 프로젝트 시작
2. **Out-of-scope 생략** — 범위 분쟁의 가장 흔한 원인
3. **리스크만 있고 대응책 없음** — 걱정 목록을 리스크 목록으로 착각
4. **측정 불가 성공 기준** — "향상", "개선", "안정화"
5. **마일스톤에 날짜 없음** — "1차", "2차"만 있고 날짜 없음
6. **전제조건을 리스크에 연결 안 함** — 전제 붕괴 시 대응 없음
7. **예산에 예비비 없음** — 변경 발생 시 처리 방법 없음
